# 首周启动：从今天到第一次手动发布

第一周只有一个目标：跑通两条真实主题的完整循环。不要同时追求爆款、付费视频、会员产品和全自动分发。

## 先固定两个时间

1. 选一个每周重复的 150 分钟半天，用于确认主题和录制。
2. 选一个每天重复的十分钟窗口，用于审批队列。

时间未固定前，不要让数字员工大量起草；否则你只会得到一堆过期草稿。

## 首周主题提示

从下面选择你**本周真实做过**的两个方向；没有真实经历就换题，不要照抄。首个四周周期应完成六条职场 AI 主题、两条产品经理主题；首周可以两条都选职场 AI，避免把长期 80/20 定位机械地做成每周 50/50。

| 比例 | 主题提示 | 录屏应证明什么 |
| --- | --- | --- |
| 80% 职场 AI 能力 | “我把一个反复出现的工作任务，从聊天式求助变成了可复用工作流。” | 输入是什么、AI 如何参与、产物如何复用、什么情况下失败。 |
| 80% 职场 AI 能力 | “我不再把 AI 输出直接交付，而是用一个检查点把它变成可验证的职业成果。” | 一个质量检查点、失败样例，以及被修正后的可复用结果。 |
| 20% 产品经理进阶 | “我判断一个 AI 功能值不值得做，不先看演示效果，而先看这三个可验证条件。” | 一个真实产品判断、取舍依据、被否决的替代方案。 |

## 第 0 天：创建两个主题目录

在仓库根目录执行；把 `<主题短名>` 换成英文短名。

```powershell
$week = "2026-W35"
$topic = "replace-with-your-topic"
New-Item -ItemType Directory -Force "content/$week/$topic"
Copy-Item templates/core-theme-brief.md "content/$week/$topic/theme-brief.md"
Copy-Item templates/content-package-starter.json "content/$week/$topic/content-package.json"
```

对第二条主题重复一次。然后把两条主题写进 `templates/weekly-content-plan.md` 的副本。

## 第 1–3 天：只准备，不发布

1. 研究员写 `research-notes.md`，选题编辑填主题简报。
2. 你在每日十分钟队列只确认：职业问题、真实演示、你的判断。
3. 脚本编辑准备录制提纲；没有你的事实确认，不进入录制。

## 固定半天：录制与草稿预览

1. 录制两条 8–12 分钟长视频；每条允许一次补录。
2. 剪辑简报员从原始录屏提炼 B 站长版和三个短版草稿。
3. 分发编排员只为缺失的新平台版本填写 `releaseApproval: "pending"`，绝不覆盖已有审批。
4. GitHub 维护员准备一个真实可公开的基础资产；不能公开就暂不填 `public`。

## 手动发布前：运行门槛检查

在你把内容包的真实字段补齐后，先运行预检：

```powershell
npm run content:check -- content/2026-W35/<主题短名>/content-package.json
```

先运行预检；若看到 `awaiting-owner-approval`，你手动确认平台草稿并更新对应 `releaseApproval`，再重跑到 `status: "ready"`。此后才由你在各平台手动发布。若报告给出其他状态，只执行 `nextStep` 指向的那一项，不绕过检查。

## 发布后：把证据带回下一周

48 小时后，填写 `weekly-review.md`。只保留具体问题、收藏原因、使用反馈和 GitHub 信号；把它们变成下一周 `inbox` 里的候选主题。

## 你现在只需发给我这五行

```text
1. 我本周真实用 AI 完成过的一个职业任务：
2. 我能录屏展示的过程或产物：
3. 我的真实判断（允许不确定）：
4. 我愿意公开的失败、限制或反例：
5. 我固定的 150 分钟半天和每日十分钟时段：
```

收到后，我就能为你创建第一条真实主题的简报、内容包和每日审批队列；没有这五项，我不会编造你的个人 IP 故事。

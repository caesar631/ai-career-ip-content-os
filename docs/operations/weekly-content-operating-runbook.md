# 每周内容运营手册

这是把“数字员工团队”变成实际节奏的手册，不是自动化发布系统。它的目标是：你每周录两条真实核心内容、每天只花十分钟做判断；其他准备工作有明确交接物可审。

## 先理解什么叫“24 小时工作”

数字员工不是会自行登录账号、代替你表达的真人。它们是随时可被 Codex 任务或定时提醒唤起的六个工作单元。团队能持续运转，靠的是三个固定触发点：

1. **每周启动**：你确认两条主题和一个 GitHub 更新目标。
2. **每日十分钟审批**：你只处理需要你的选择、事实确认、发布或费用批准。
3. **发布后 48 小时复盘**：团队把具体问题、收藏和使用反馈写回下周主题池。

没有这三个触发点，仓库只是一套模板；有了它们，研究、草稿和复盘才会持续累积。

## 责任边界

| 工作单元 | 输入 | 交接物 | 不能做的事 |
| --- | --- | --- | --- |
| 研究员 | 你的真实工作、评论问题、公开资料 | `research-notes.md`：事实、来源、反例、可演示机会 | 不能把未验证信息写成事实。 |
| 选题编辑 | 研究卡和你的职业目标 | `theme-brief.md`：职业问题、受众、承诺、反直觉判断 | 不能替你编造经历或观点。 |
| 脚本编辑 | 已确认主题简报 | `long-video-script.md`：8–12 分钟口播与录屏节拍 | 不能把草稿当成你的最终表达。 |
| 剪辑简报员 | 原始录屏和脚本 | `editing-brief.md`：长版章节、三个短版切点、封面文字建议 | 不能伪造录屏、案例或结果。 |
| 分发编排员 | 已剪出的素材和批准的文案 | 四个平台的草稿说明、标题、CTA、标签与检查结果 | 不能自动发布、登录账号或回复评论。 |
| 复盘员兼 GitHub 维护员 | 发布后数据、评论、基础资产改动 | `weekly-review.md`、GitHub 更新草稿、下周问题池 | 不能把播放量当作唯一结论，不能承诺增长。 |

你是**内容主理人**，只保留五件不可委托的事：个人经历与价值判断、录制、事实最终确认、发布审批、真实互动。付费视频还需要你对完整简报做明确批准。

## 一条主题的阶段与交接

每个主题放在 `content/<年份-周数>/<主题短名>/`。同一主题只往前走，不在多个表格里复制状态。

```text
inbox
  → research-ready
  → recording-ready
  → recorded
  → draft-ready
  → owner-approval
  → published
  → reviewed
```

| 阶段 | 谁推进 | 可见交接物 | 你需要决定什么 |
| --- | --- | --- | --- |
| `inbox` | 研究员 | 一个来自工作、评论或反馈的原始问题 | 值不值得研究。 |
| `research-ready` | 研究员 | 可核对的事实、限制和可录屏演示 | 事实是否可靠。 |
| `recording-ready` | 选题/脚本编辑 | 主题简报、长视频提纲、录屏路径 | 是否是你的真实判断。 |
| `recorded` | 内容主理人 | 原始 8–12 分钟录屏 | 无；只确认可进入剪辑。 |
| `draft-ready` | 剪辑/分发编排员 | B 站长版与小红书、抖音、视频号草稿 | 标题、封面和表达是否准确。 |
| `owner-approval` | 内容主理人 | 通过内容包检查的报告 | 哪些平台现在手动发布。 |
| `published` | 内容主理人 | 实际发布链接和时间 | 是否需要补充评论互动。 |
| `reviewed` | 复盘员 | 48 小时反馈与下一轮问题 | 下周保留、加强或停止什么。 |

## 每日十分钟审批

不要打开一堆草稿。每天只看一张 `daily-approval-queue.md`，最多处理三项：

| 分钟 | 你做什么 | 允许的结论 |
| --- | --- | --- |
| 0–2 | 看“今天需要我决定什么” | 批准、否决或要求补一个事实。 |
| 2–5 | 看一条主题的职业问题、演示、判断 | 确认它是不是你的真实观点。 |
| 5–8 | 看一个平台草稿的标题、封面、CTA | 放行到手动发布，或要求改写。 |
| 8–10 | 看一条反馈或 GitHub 变更 | 归入下周问题池，或要求公开修正。 |

队列为空时什么都不做。不要为了“勤奋”新增待办。

## 每周固定半天：150 分钟版本

选择一个固定的 2–3 小时窗口；首月建议每周同一时段。团队必须在该窗口前把 `recording-ready` 材料准备好。

| 时间 | 你做什么 | 数字员工应已准备好 |
| --- | --- | --- |
| 0–15 分钟 | 从问题池中确认两条主题 | 两份主题简报和各自的反例。 |
| 15–30 分钟 | 修改成你的观点与故事 | 8–12 分钟提纲、录屏演示步骤。 |
| 30–90 分钟 | 录制两条核心视频，每条最多一次补录 | 无；你的录屏是不可替代输入。 |
| 90–115 分钟 | 预览长版章节、三个短版切点和封面标题 | 剪辑简报和四平台草稿。 |
| 115–135 分钟 | 确认公开基础资产与 GitHub 更新 | 模板/工作流/复盘的改动说明。 |
| 135–150 分钟 | 运行就绪检查，决定本周手动发布顺序 | 每个主题的 `content-package.json` 与检查报告。 |

## 发布前唯一门槛

每个主题都要有 `content-package.json`。在 `owner-approval` 前运行：

```powershell
npm run content:check -- content/<年份-周数>/<主题短名>/content-package.json
```

只有 `status: "ready"` 才表示内容材料、四个平台版本、公开基础资产、发布审批与付费视频门禁都通过。输出里的 `platformVersionStatuses` 告诉你逐个平台情况，`nextStep` 告诉你此刻最该做的一件事。

这不是发布命令。发布始终由你在各平台手动完成；评论、私信和任何付费视频生成也不自动执行。

## 发布后 48 小时复盘

复盘员只收集可行动信号：具体问题、收藏原因、反对意见、模板使用反馈、GitHub Star/Fork/Issue。每条信号要回答：

1. 观众卡在哪个职业任务？
2. 这说明标题、演示还是判断需要改？
3. 下周是加深、反驳、制作模板，还是停止这个角度？

首月只追踪四个指标：两条主题是否稳定交付、是否收到具体问题、公开基础资产是否被实际使用、你的职业判断是否因反馈改变。粉丝数保留为背景数据，不用来驱动选题。

## 今天就能启动

1. 选一个你本周真实做过的 AI 工作：例如“用 AI 把反复研究变成可复用工作流”。
2. 复制核心主题简报模板，先用自己的话填职业问题、演示和判断；任何你没有亲历的内容都留空。
3. 在下一次固定半天录制一条 8–12 分钟长视频，不用买视频生成额度。
4. 让团队基于原始录屏准备三条短版草稿与一个 GitHub 基础资产。
5. 用每日十分钟队列做决定；通过检查后，你亲自点击发布。

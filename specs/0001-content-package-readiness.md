# 内容包就绪检查

## Problem Statement

作为正在公开构建个人 IP 的内容主理人，我每周需要把两条真实 AI 实践变成可发布内容。一个核心主题要同时服务小红书、抖音、视频号、B 站和 GitHub，但很容易遗漏某个平台版本、基础资产、发布审批或付费视频的成本批准。

我不需要一个会替我自动发言的账号。我需要在发布前清楚看见一个核心主题是否完整、还缺什么，以及能否安全公开。没有这一层检查，数字员工团队会制造大量草稿，却无法稳定交付可信内容。

## Solution

提供“内容包就绪检查”。内容主理人或数字员工以一个核心主题为单位登记职业问题、演示、判断、平台版本、基础资产、发布审批和付费视频生成简报。系统对该内容包给出一个对外可理解的结果：`可发布`、`待补全`、`待主理人审批` 或 `被付费视频门禁阻塞`，并列出缺失项和下一步。

首版只检查发布准备度，不连接任何社交平台，也不自动发布、自动互动或调用付费视频模型。它让每周两条核心主题具有同一套可验证的交付标准。

## User Stories

1. 作为内容主理人，我想为一个核心主题记录一个职业问题、一次演示和一个判断，以便内容始终基于真实实践。
2. 作为内容主理人，我想为核心主题登记小红书版本，以便检查它是否已准备好被收藏和理解。
3. 作为内容主理人，我想为核心主题登记抖音版本，以便短视频分发不遗漏。
4. 作为内容主理人，我想为核心主题登记视频号版本，以便我的视频号发布准备度可见。
5. 作为内容主理人，我想为核心主题登记 B 站完整版本，以便保留可解释的长视频证据。
6. 作为内容主理人，我想关联一项基础资产，以便受众能在 GitHub 看到并尝试真实成果。
7. 作为内容主理人，我想标记每个公开版本是否已批准，以便数字员工不能把草稿当作可以公开的内容。
8. 作为内容主理人，我想把“需要付费视频”明确标出，以便我能在充值和生成前审查成本与验收条件。
9. 作为内容主理人，我想在付费视频生成简报不完整或未批准时看到阻塞提示，以便不会产生未授权费用。
10. 作为数字员工，我想录入和更新内容包草稿，以便持续完成研究、剪辑、分发准备和资产维护。
11. 作为数字员工，我想得到结构化的缺失项清单，以便优先补齐真正阻塞发布的工作。
12. 作为内容主理人，我想一次查看某个内容包的总状态和各渠道状态，以便在每日十分钟审批中快速决定是否发布。
13. 作为内容主理人，我想在内容包完整但仍未审批时看到“待主理人审批”，以便系统不会把完成误报为已发布。
14. 作为内容主理人，我想在所有必要内容、资产和审批都齐全时看到“可发布”，以便将精力留给真实互动。
15. 作为内容主理人，我想在某个内容包没有任何付费视频需求时不受视频门禁影响，以便录屏、代码和原型演示可以低成本运行。
16. 作为内容主理人，我想让检查结果说明为什么不可发布，而不是只给出失败标记，以便下周可以改进内容工作流。
17. 作为未来会员用户，我想确认公开基础资产与会员资产没有混在一起，以便知道免费试用和付费内容的边界。
18. 作为项目维护者，我想用一组可重复的检查场景验证规则，以便日后新增数字员工时不破坏人工审批和成本门禁。

## Implementation Decisions

- 建立“内容包”这一唯一输入边界。内容包必须包含核心主题的职业问题、演示和判断；这三项缺一不可。
- 默认发布目标为小红书、抖音、视频号和 B 站。它们可以共享同一核心录屏来源，但必须有各自的发布准备记录。
- 一个内容包必须关联一项公开基础资产。基础资产与会员资产使用不同的可见性标记，首版不提供会员交付或支付功能。
- 发布审批以每个发布目标为单位记录。系统只能报告准备状态；实际发布始终由内容主理人完成。
- 付费视频需求以显式门禁记录处理。若需要付费视频，则必须填写用途、数量、验收标准、成本和停止条件，并取得主理人批准；否则内容包处于阻塞状态。
- 就绪状态按阻塞优先级计算：缺少核心内容、平台版本或基础资产时为“待补全”；付费视频简报不完整或未批准时为“被付费视频门禁阻塞”；内容完整但存在未批准发布目标时为“待主理人审批”；全部满足时为“可发布”。
- 对外入口只需提供一次内容包检查及其可读报告。首版不做账户登录、多用户协作、远程数据存储或平台 API 集成。
- 以可被版本控制的内容包样例作为首版数据来源。数字员工可以起草或更新样例，但不拥有绕过审批的能力。
- 先支持单个内容包的端到端检查；每周两条主题的节奏由多个内容包重复使用此入口实现，而不是单独建立周计划子系统。

## Testing Decisions

- 测试只观察内容包输入与就绪报告输出，不检查内部函数、存储结构或实现顺序。
- 最高测试切口是“执行一次内容包就绪检查并读取结构化、可读的结果”。所有验收场景都通过该入口验证。
- 至少覆盖以下外部行为：完整且已批准的内容包报告“可发布”；缺少职业问题、演示、判断、任一发布目标或基础资产时报告“待补全”及具体缺失项；完整但未批准时报告“待主理人审批”；需要付费视频但简报缺失或未批准时报告“被付费视频门禁阻塞”；不需要付费视频的录屏内容不受该门禁影响。
- 每个测试样例使用一个完整、可读的内容包场景，便于内容主理人验证其是否符合真实工作方式。
- 初始代码库没有可复用测试先例；本规格建立的端到端入口将成为后续内容包功能的测试先例。

## Out of Scope

- 直接发布到小红书、抖音、视频号或 B 站。
- 自动回复评论、私信、销售或公开表达观点。
- 调用 Minimax H3 或任何其他付费视频模型。
- 会员支付、权益发放、社群或客服系统。
- 粉丝预测、外部平台数据抓取、复杂增长仪表盘。
- 真实客户资料、第三方隐私数据或未授权素材的存储和公开。
- 将数字员工描述为可独立承担法律、商业或公开表达责任的真人员工。

## Further Notes

- 本规格导入了此前 PRD 中已确认的业务方向：80% 职场 AI 能力、20% 产品经理进阶；每周两条 8–12 分钟录屏核心内容；GitHub 基础资产公开、完整 SOP 与进阶工作流留给后续会员层；每日由内容主理人集中审批。
- 首版的成功信号是连续四周稳定交付、获得具体问题和收藏、以及 GitHub 的 Star、Fork 或使用反馈；不以粉丝数作为首要验收指标。
- 付费视频只在录屏、代码、产品原型或静态素材无法满足内容目标时考虑，并遵守事前审批与事后验收。

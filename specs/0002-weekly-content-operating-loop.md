# 每周内容运营循环

## Problem Statement

内容包就绪检查解决了“某条内容能否进入发布审批”的问题，但账号还缺少一条可持续的生产节奏：谁在什么时候准备什么、内容主理人每天十分钟看什么、两小时到三小时的集中录制如何变成四个平台的原生草稿，以及发布后的反馈怎样回到下一周。

如果数字员工只产生零散草稿，主理人仍然要临时找选题、判断优先级和追踪进度，个人 IP 不会稳定增长。首个运营循环必须保护主理人的真实声音，同时让研究、起草、剪辑简报、分发准备、GitHub 维护和复盘有可交接的产物。

## Solution

建立一个以“周”为单位的内容运营循环。每周交付两条 8–12 分钟核心录屏主题、每条主题的小红书/抖音/视频号/B 站草稿版本、一次 GitHub 公开基础资产更新和一次职业判断复盘。每个主题均有一个可检查的内容包。

内容主理人保留观点、个人故事、关键判断、录制、最终发布和真实互动；数字员工只准备材料、形成草稿、维护资产和生成复盘。每天仅需要一个十分钟审批队列；每周固定一个 2–3 小时半天完成选题确认、录制和草稿放行。

## User Stories

1. 作为内容主理人，我想在固定半天一次性确认两条主题并录制长视频，以便不被每天的临时创作打断。
2. 作为内容主理人，我想每天只看到需要我做决定的少量事项，以便十分钟内完成审批。
3. 作为内容主理人，我想让每个主题先有真实职业问题、演示和判断，再要求数字员工改编，以便账号不变成泛 AI 资讯搬运。
4. 作为内容主理人，我想由数字员工把同一核心录屏准备成四个平台的原生草稿，以便一份真实工作获得多次分发价值。
5. 作为内容主理人，我想把可公开试用的模板、工作流或复盘同步到 GitHub，以便积累可验证的账户资产。
6. 作为内容主理人，我想每周复盘职业判断、失败和受众提出的具体问题，以便内容和职业能力一起进步。
7. 作为数字员工，我想收到结构化交接物和明确的停止边界，以便不会代替主理人发布、互动或调用付费视频模型。

## Implementation Decisions

- 内容比例固定为约 80% 职场 AI 能力、20% 产品经理进阶；首月不以粉丝数作为主指标。
- 每周只安排两条核心主题和一次 GitHub 更新。每条主题以一个 8–12 分钟核心录屏为源；B 站保留长版，小红书、抖音和视频号改编为原生短版草稿。
- 数字员工采用六个明确工作单元：研究员、选题编辑、脚本编辑、剪辑简报员、分发编排员和复盘员。它们交接文件，不拥有账号发布权、评论回复权或费用审批权。
- 以 `inbox → research-ready → recording-ready → recorded → draft-ready → owner-approval → published → reviewed` 作为每个主题的可见阶段。只有 `owner-approval` 后才能由主理人手动发布。
- 每日审批队列只能包含三类事项：选择/否决、事实或观点确认、发布或费用批准。没有需要主理人决定的事项时，数字员工继续准备，不制造提醒。
- 每周固定半天依次完成：选题确认、两条长视频录制、分发草稿预览、GitHub 更新确认。其他时间的数字员工工作必须产出可以在十分钟内审阅的材料。
- 使用内容包就绪检查器作为发布前门槛。付费视频默认不需要；只有录屏、代码或产品原型不能表达核心判断时才进入付费视频生成简报门禁。
- GitHub 只公开基础资产和真实复盘；完整 SOP、进阶工作流与答疑在首月只记录为未来会员资产，不交付、不收费。

## Testing Decisions

- 运营手册必须给出可复制的周计划、主题简报、每日审批和周复盘模板。
- 每份主题简报必须能映射到内容包中的职业问题、演示、判断、平台版本、基础资产和审批字段。
- 首周演练使用不需要付费视频的主题；所有发布版本先停在草稿和主理人审批状态。
- 对运营手册的验收是：主理人能在不借助额外解释的情况下，按照“今天、半天、发布后”三个入口开始执行。

## Out of Scope

- 自动发布、自动回复评论或私信。
- 平台账号登录、Cookie 保存、平台 API 接入或批量上传。
- 调用 Minimax H3、购买积分或任何付费视频生成。
- 会员支付、交付、社群或客服。
- 用虚构故事或未经确认的职业经历替主理人发言。

## Further Notes

- 首周主题必须来自主理人刚刚做过或正在做的真实工作；数字员工可以帮助提炼，但不能编造个人经验。
- 成功信号按优先级为：稳定交付、收藏或具体问题、GitHub Star/Fork/可验证使用反馈；粉丝数在首月只作背景数据。
